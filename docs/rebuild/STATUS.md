## stage 04A — ตรวจเว็บแบบเร็ว
**ปัญหาเดิม:** `POST /audit` เรียก `site_health.run_checks` ระหว่างที่ผู้ใช้รอ (ได้ถึง ~40 request × timeout 20 วินาที) ไม่มีสถานะระหว่างทาง ไม่มีเวลารวมสูงสุด
**ใหม่ (เมื่อ `snapshot_v2` active):**
- `POST /audit` → ออก token, นับโควตาทันที (ตั้ง `audit_at` ตอนเข้าคิว), `snapshot.start()` แล้ว redirect ไป `/audit/{token}` ทันที
- `app/snapshot.py` รันตัวตรวจเดิมเบื้องหลังด้วย timeout 10 วินาที/request และเวลารวม 90 วินาที (ปรับได้ที่ settings `snapshot_timeout_s`, `snapshot_budget_s`) · อ่านหน้าเว็บไม่เกิน 5 หน้า (MAX_CRAWL เดิม)
- เก็บสถานะใน `leads.snapshot_json` (คอลัมน์ใหม่ เพิ่มอย่างเดียว): queued → running → completed / partial / failed · ทีละขั้น 6 ขั้น: pending → running → done / skipped / failed
- `/audit/{token}` ระหว่างตรวจ = หน้าสถานะ `mk/snapshot.html` (รีเฟรชเองทุก 3 วินาทีด้วย meta refresh ไม่ต้องใช้ JS, noindex, no-store, ไม่มี %) · ล้ม = บอกเหตุผล + ปุ่มตรวจใหม่ · เสร็จ = หน้าผลเดิม พร้อมแถบ "ตรวจได้บางส่วน" หรือ "เปิดหน้าแรกไม่ได้" ถ้าเป็นกรณีนั้น
- กดซ้ำระหว่างตรวจ = ไม่เริ่มซ้ำ · ค้างเกิน 5 นาที (process ตาย/รีสตาร์ต) = แสดงว่าล้ม ไม่หลอกว่ายังทำ และเริ่มใหม่ได้
- `site_health.run_checks` รับ `progress`, `timeout`, `deadline` เพิ่ม (ค่าเริ่มต้น = พฤติกรรมเดิม) · หมดเวลา = คืน `partial` + `skipped` ไม่นับส่วนที่ไม่ได้ตรวจเป็นไม่ผ่าน
- `pipeline.save_lead_audit()` แยกออกจาก `run_lead_audit` ใช้ร่วมกัน (พฤติกรรมเดิมไม่เปลี่ยน)
- หลังตรวจเร็วเสร็จ เริ่มรายงานเต็มชั้น 1 แบบเดิม (`deep_audit.start`) — ไม่เปลี่ยนเพดานหรือสิทธิ์เดิม
**เทสต์:** `snapshot_smoke.py` — flag ปิด = แบบเดิม, สำเร็จ, หน้าสถานะ (ไม่มี %, รีเฟรชเอง, noindex), กดซ้ำ, ค้าง, partial, เปิดเว็บไม่ได้, ล้ม + ตรวจใหม่, URL ภายใน, โควตาตอนเข้าคิว, deadline จริงใน `run_checks`
**ข้อจำกัดที่ยังเหลือ:**
- งานเป็น thread ใน process เดียว (คิวถาวรรอ stage 10) · ล็อกกันซ้ำได้เฉพาะใน process เดียว ถ้ารันหลาย worker อาจเริ่มซ้ำได้
- request ที่กำลังยิงอยู่ตอนหมดเวลารวมยังรอจน timeout ของมันเอง (≤10 วินาที) · ไม่มีเพดานขนาดไฟล์ที่ดาวน์โหลด (httpx อ่านทั้งไฟล์)
- ตัวตรวจเดิมเรียก Serper (มีค่าใช้จ่าย) ถ้าตั้ง backend เป็น serper — เป็นพฤติกรรมเดิม ไม่ได้เปลี่ยนในขั้นนี้
- การตรวจเร็วยังไม่ได้ "เลือกหน้าที่เกี่ยวข้อง" (เช่นหน้าบริการ) แบบเจาะจง ใช้ลำดับลิงก์ของตัวตรวจเดิม
- หน้าสถานะ `mk/snapshot.html` เป็นภาษาไทยอย่างเดียว (ผู้ใช้ภาษาอื่นจะเห็นหน้าสถานะเป็นไทยระหว่างรอ) · แถบแจ้งบนหน้าผลแปลครบ 5 ภาษาแล้ว (`app/i18n/audit.json`)

### Migration / rollback
- ตารางใหม่ 1 ตาราง `line_events_seen(event_id PK, seen_at)` สร้างผ่าน `CREATE TABLE IF NOT EXISTS` ใน `init_db` (เพิ่มอย่างเดียว) · rollback: revert โค้ด ตารางค้างไว้ได้ไม่กระทบ
- ปิดตัวกัน SSRF ชั่วคราว: `GEO_NETGUARD=0` · ส่วนการไม่ reuse ลีดไม่มี flag (เป็นการแก้ช่องรั่ว)

### ผลข้างเคียงที่ตั้งใจ
- ลีดซ้ำโดเมนเพิ่มขึ้น (คนละคนตรวจโดเมนเดียวกัน = คนละลีด) → ทีมขายอาจเห็นโดเมนเดียวกันหลายแถว · รวมลีดเป็นงานของ stage 09
- คนที่ตรวจโดเมนเดียวกันจากคนละ IP จะทำให้ระบบไต่เว็บซ้ำ (จำกัดด้วย quota 5/IP/วัน เดิม)
- LINE event ถูกจองก่อนประมวลผล → ถ้าประมวลผลล้มกลางทาง LINE ส่งซ้ำจะไม่ถูกทำอีก (เลือกไม่ตอบซ้ำมากกว่าตอบสองครั้ง)

### ข้อจำกัดที่ยังเหลือ
