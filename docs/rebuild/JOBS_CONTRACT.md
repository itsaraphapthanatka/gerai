## 2. คิวงาน (`jobs`)
- สถานะ: `queued` → `running` → `succeeded` / `dead` / `cancelled` (ล้มแบบลองใหม่ได้กลับไป `queued`)
- **การรับประกัน: at-least-once** ไม่ใช่ exactly-once · งานอาจถูกทำซ้ำได้เมื่อ worker ล่มหลังทำผลแต่ก่อนบันทึก → ผลภายนอกทุกอย่างต้อง idempotent (outbox `idem_key`, การอนุมัติจำว่างานไหนใช้, เช็กสถานะก่อนทำ)
- `idem_key` UNIQUE: เข้าคิวซ้ำ = ได้งานเดิม (เช่น `deep_ai:{lead}:{วัน}`)
- **claim** = UPDATE แบบ compare-and-set (`WHERE status='queued'`) → หลาย worker/หลาย scheduler แย่งงานเดียวกัน ได้คนเดียว
- **lease** 15 นาที + heartbeat · lease หมด = `recover()` คืนเข้าคิว (หรือ `dead` ถ้าครบจำนวนครั้ง) · worker เก่าที่ฟื้นมาบันทึกผลทับไม่ได้ (ต้องถือ lease อยู่)
- ลองใหม่: เว้น 30 วิ × 2^(ครั้ง-1) สูงสุด 1 ชม. · ครบ `max_attempts` = `dead` (หน้า `/admin/jobs` กดสั่งใหม่/ยกเลิกได้)
- **เลื่อน (defer)** ไม่นับเป็นความพยายาม: รอข้อมูลก่อนหน้า, รองบวันถัดไป, จุดหยุด · เลื่อนรวมเกิน 72 ชม. = `dead`
- **ยกเลิก:** รอทำ/ล้ม = ยกเลิกทันที · กำลังทำ = ตั้ง `cancel_requested` ให้ handler หยุดก่อนทำผลภายนอก (ทำไปแล้ว = ไม่ย้อน)
- worker: `jobs.run_once()` เรียกจาก (ก) `kick()` หลังเข้าคิว (thread หนึ่งรอบ) (ข) ลูป `geo-autorun` (ค) `run_monitors.py --jobs` — ซ้อนกันได้ · flag ปิด = worker ไม่ทำอะไร งานค้างรอในคิว

## 3. จุดหยุด (`job_pauses`)
`global` (kill switch) · `workflow` (ประเภทงาน) · `channel` · `account` (ลีด) — **เช็กทั้งตอนเข้าคิว (ไม่รับ) และตอนจะทำ (เลื่อน 5 นาที ไม่นับความพยายาม)** · กดที่ `/admin/jobs` · แยกจาก `agents_paused` เดิม (ยังทำงานแบบเดิม)

## 4. งบ (`budget_reservations`)
- จองก่อนเรียกบริการที่เสียเงิน → `settle` ด้วยค่าจริง / `release` เมื่อล้มหรือยกเลิก · จองค้างเกิน 2 ชม. โดยงานไม่ได้รันอยู่ = คืนอัตโนมัติ
- **atomic:** ใส่แถวก่อนแล้วรวมยอดในธุรกรรมเดียว เกินเพดาน = ยกเลิกทั้งธุรกรรม (SQLite: write lock · Postgres: `pg_advisory_xact_lock` ต่อ budget_key) · เทสต์จองพร้อมกัน 12 ราย เพดาน 5 → ได้ 5 พอดี
- เพดาน `ai_usd` ต่อวัน (เวลาไทย): setting `budget_ai_usd_daily` · ไม่ตั้ง = `deep_ai_daily` (เพดานจำนวนรายเดิม ค่าเริ่มต้น 5) × $1.20 (ค่าประมาณต่อครั้ง วัดจริง ≈ $1.15) → ค่าเริ่มต้น $6/วัน
- งบหมด: ไม่เรียก AI · รายงานขึ้น "ครบงบทดสอบ AI วันนี้ — ระบบจะวัดให้วันถัดไป" · งานเลื่อนไป 00:05 วันถัดไป
- เพดานจำนวนรายต่อวันเดิม (`ai_daily`) ยังใช้อยู่ใน `run_ai` เหมือนเดิม (สองชั้น)
- **ค่าใช้จ่ายจริงต่อครั้งอาจเกินที่จอง** (จอง $1.20 แต่ใช้จริงมากกว่า) → ยอดจริงถูกนับ แต่งานที่กำลังรันอยู่ไม่ถูกหยุดกลางทาง

## 5. การอนุมัติ (`approvals`)
ผูกกับ: action · ลีด · ผู้รับ (เก็บเป็น hash) · ช่องทาง · hash เนื้อหา + version · หลักฐาน · ค่าใช้จ่ายสูงสุด · นโยบาย · ผู้อนุมัติ · วันหมดอายุ
- ใช้ได้ **ครั้งเดียว** แบบ atomic (CAS) · งานเดิมที่ทำซ้ำหลังเครื่องล่ม = ผ่าน (จำ `consumed_job_id`)
- เนื้อหา/ผู้รับ/ช่องทาง/ลีด/version เปลี่ยน · เกินค่าใช้จ่าย · หมดอายุ · ถูกถอน = ใช้ไม่ได้ → งาน `dead` ทันที (ไม่ลองใหม่)
- stage 10 ยังไม่ผูกกับ `decisions` เดิม — จะใช้เมื่อย้ายงานส่งข้อความทีละตระกูล

## 6. outbox (`outbox`)
- ผลภายนอกเขียนผ่าน `outbox_put(idem_key)` · `idem_key` เดิม = ไม่สร้างซ้ำ
- **stage 10 เป็นโหมดทดสอบเท่านั้น:** `mode='test'` บันทึกอย่างเดียว ไม่มีตัวส่ง · ผู้รับเก็บเป็น hash · มีงานตัวอย่าง `test_message` (ต้องมีการอนุมัติที่ตรงเป๊ะ + เช็กการขอไม่รับตอนจะทำ) เพื่อทดสอบเส้นทางทั้งหมด

## 7. งานที่ย้ายแล้ว: `deep_ai` (ทดสอบ AI ของรายงาน)
- flag ปิด: `deep_audit.start(ai=True)` ใช้ thread แบบเดิม
- flag เปิด: เข้าคิว `deep_ai:{lead}:{วัน}` (สั่งวัดใหม่ = งานใหม่) · รายงานขึ้น "อยู่ในคิว" · thread เดิม **ไม่** เรียก AI (ไม่ทำสองทางพร้อมกัน) · ชั้นแรก (ไต่เว็บ+อันดับ) ยังใช้ thread เดิม
- handler: มีผลใหม่กว่างานแล้ว = ข้าม · ชั้นแรกยังไม่เสร็จ = เลื่อน 1 นาที · จองงบ → `run_ai` → ปิดยอดด้วยค่าจริง / คืนงบเมื่อล้ม · ลองใหม่สูงสุด 2 ครั้ง (`run_ai` บันทึกสถานะ error ไว้ในรายงาน)

## 7a. นโยบายการทดสอบ AI แบบเสียเงิน (stage 04C · `app/ai_tests.py`)
- **สวิตช์ `ai_live_tests` ค่าเริ่มต้นปิด** (กดที่ `/admin/jobs` · หมวดตั้งค่า): ปิด = ไม่เรียก AI รายงานขึ้น "ยังไม่เปิดการทดสอบ AI แบบเสียเงิน" · ปิดหลังเข้าคิว = งานยกเลิกตัวเองก่อนเรียก
- **สิทธิ์ตามเหตุผลที่สั่ง:** ลูกค้าขอแผน / ทิ้งช่องทางติดต่อ / ขอนัด = อัตโนมัติ 1 ครั้งต่อลีดต่อ 30 วัน · ทีมกด (หน้าลีด หรือสั่งผ่าน CEO chat) = 3 ครั้งต่อลีดต่อ 30 วัน · ตอบกลับเฉย ๆ / เอเจนต์ AI สั่ง (`orchestrator` ai_report) / ไม่ระบุ = ไม่ทำเอง รายงานขึ้น "ทีมกดสั่งได้ในหน้าลีด" · ขอไม่รับ = ไม่ทำ
- ไม่มีคำค้นและลูกค้ายังไม่ยืนยันบริการหลัก = `needs_input` (ไม่เดาคำถามเอง)
- **ลองใหม่ไม่จ่ายซ้ำ:** คำตอบที่สำเร็จเก็บในตาราง `ai_answer_cache` ผูกกับ `idem_key` ของงาน → งานเดิมที่ทำซ้ำหลังล่มใช้คำตอบเดิม · ยอดงบนับตามที่จ่ายจริงต่อรอบ (รอบที่ล่มก็นับ ไม่คืนงบที่จ่ายไปแล้ว)
- ไม่มีคีย์ผู้ให้บริการ = `not_configured` → รายงานเป็น "ยังไม่ได้ทดสอบ" (ไม่ใช่ "ระบบไม่พร้อม") · ผู้ให้บริการไม่ตอบทุกข้อ = "ระบบไม่พร้อม" ไม่มีตัวเลข · ทีมยกเลิก = `cancelled`
- สถานะใน `deep_ai_json`: queued · running · done (ครบ/บางส่วน) · disabled · needs_input · awaiting_staff · not_configured · cancelled · error
- ค่าประมาณแสดงที่ `/admin/jobs`: $1.20 ต่อรายงาน (20 คำถาม) · งบวันละ = `budget_ai_usd_daily` หรือเพดานจำนวนเดิม × $1.20
- **เส้นทาง thread เดิม (flag `durable_jobs` ปิด) ไม่เปลี่ยน** — ตอนนี้ production ยังถาม AI ตามเพดานรายวันเดิม (5 ราย/วัน) ทุกครั้งที่ลูกค้าตอบกลับ/ขอแผน/ทิ้งช่องทางติดต่อ

## 8. เปิดใช้ / ย้อนกลับ
- เปิด: ตั้ง `budget_ai_usd_daily` ให้ชัด → เปิด `durable_jobs` บน staging → ดู `/admin/jobs` · ถ้ามี cron ตั้ง `run_monitors.py --jobs` ทุก 1 นาทีได้ (ไม่บังคับ: `kick` + autorun ก็พอ)
- **ปิด flag ระหว่างมีงานค้าง:** worker หยุด งานค้างรอในคิว (ไม่หาย ไม่ทำ) · ลีดที่ค้าง "อยู่ในคิว" จะถูกทำแบบ thread เดิมเมื่อมีคนเรียก `start` อีกครั้ง · เปิด flag กลับ: งานเดิมข้ามเองถ้ามีผลใหม่กว่าแล้ว
- ย้อนโค้ด: ตารางใหม่อยู่ได้ (โค้ดเก่าไม่อ่าน) · ไม่มีงานส่งข้อความในคิว จึงไม่มีอะไรถูกส่งซ้ำ/เปิดกลับ
- งานในคิวเก็บ `kind` + payload JSON — เวอร์ชันใหม่ต้องอ่าน payload เก่าได้ (เพิ่มฟิลด์ได้ ห้ามเปลี่ยนความหมาย) · ประเภทที่ไม่รู้จัก = dead พร้อมเหตุผล

## 9. ยังไม่ได้ทำ / ข้อจำกัด
- ยังไม่ทดสอบบน Postgres (advisory lock / ON CONFLICT / RETURNING ใช้ได้ทั้งคู่ตามเอกสาร แต่ยังไม่ได้รัน)
- งานอื่นทั้งหมดยังเป็น thread/cron เดิม (ไม่มีลองใหม่ รีสตาร์ตแล้วหาย) → ย้ายทีละตระกูลในขั้นถัดไป ลำดับที่เสนอ: ไต่เว็บชั้นแรก → ตรวจเว็บแบบเร็ว → SoV ตามรอบ → งานส่งข้อความ (ต้องมีตัวส่งจริงผ่าน outbox + เจ้าของอนุมัติ)
- `handle_deep_ai` ไม่ส่ง heartbeat ระหว่างถาม AI (ใช้เวลาไม่กี่นาที น้อยกว่า lease 15 นาที)
- ยังไม่มีการลบงานเก่า (เสนอเก็บ 90 วัน)
- ความเข้ากันได้ของงานที่ค้างข้ามการ deploy: ทดสอบด้วยเหตุผล ไม่ได้ซ้อม deploy จริง
