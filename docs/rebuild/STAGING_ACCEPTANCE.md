# เกณฑ์ผ่านบน staging (Staging Acceptance) — stage 18

> **สถานะ: ยังไม่ได้ทำ** — ยังไม่มีเครื่อง staging ที่ยืนยันแล้ว รายการนี้คือสิ่งที่ต้องทำและเก็บหลักฐานบน staging
> ห้ามใช้ข้อมูลลูกค้าจริงที่ไม่ได้ปกปิดตัวตน และห้ามส่งข้อความจริงถึงลูกค้าเป็นการทดสอบ
> ใช้บัญชี LINE / อีเมล / WordPress / Stripe test mode ของทีมเอง

## A. ก่อนเริ่ม (ผู้ดูแลเซิร์ฟเวอร์)

- [ ] staging แยกฐานข้อมูลจาก production · `SESSION_SECRET` คนละค่ากับ production
- [ ] **ถ้าใช้ Postgres:** `pg_smoke.py` ผ่าน และ `scripts/migration_rehearsal.py` ปรับให้ชี้ Postgres แล้วผ่าน
- [ ] ถ้าใช้ไฟล์สำรองข้อมูลจริงที่ปกปิดตัวตนแล้ว ต้องได้รับอนุมัติจากเจ้าของเป็นรายครั้ง แล้วบันทึกเวลาที่วัดได้จริง (ย้าย / สำรอง / กู้)
- [ ] รันเทสต์ทั้งชุดบนเครื่อง staging แล้วแนบผล
- [ ] ตัวตั้งเวลามีเจ้าของเดียว (cron หรือ GEO_AUTORUN + `scheduler_lease`)

## C. ความปลอดภัย (ตามโค้ดจริง)

- [ ] webhook ของ LINE และ Stripe ปฏิเสธลายเซ็นผิด (เทสต์ในเครื่องผ่านแล้ว ต้องลองบน staging ด้วย)
- [ ] หน้า /audit/<token>, /q/, /admin, /app ส่ง `Cache-Control: private, no-store` และ `Referrer-Policy: no-referrer` ผ่าน proxy จริง (ตรวจว่า proxy ไม่ตัด header)
- [ ] crawler ไม่เข้าที่อยู่ภายใน (127.0.0.1, 169.254.169.254, 10.x, ::1) ของเครือข่าย staging
- [ ] **POST เดิม 131 route ยังไม่มีโทเคน CSRF** (รายการแช่ไว้ที่ `tests_data/csrf_legacy_post_routes.json`)
    - ตอนนี้กันได้ด้วย SameSite=Lax และ `origin_check` (ต้องเปิด)
    - route ใหม่ทุกตัวมีโทเคน CSRF และเทสต์จะล้มถ้ามี route ใหม่ไม่มี
- [ ] ไม่มีรหัสลับหรือข้อมูลส่วนตัวใน log ของ staging (สุ่มตรวจ)

## D. ผ่านเมื่อ

- A, B และ C ครบทุกข้อพร้อมหลักฐาน
- ไม่มีข้อเสี่ยงระดับสูงค้าง
- เจ้าของลงชื่อรับ
