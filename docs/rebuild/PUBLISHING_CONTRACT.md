# เผยแพร่ผลงาน + ผลรายเดือน + ดูแลลูกค้าต่อ (stage 16)

flag: `publish_v2` (ปิดเป็นค่าเริ่มต้น · ปิด = ปุ่มเผยแพร่ / auto-publish / รายงานแบบเดิม)
โค้ด: `app/publishing.py`, `app/retention.py` · ตาราง `publish_requests` · หน้า `/brands/<id>/publishing` · เทสต์ `publishing_smoke.py`

## 1. ประตูก่อนเผยแพร่ (`checks`)

| ข้อ | ผ่านเมื่อ |
|---|---|
| ข้อมูลธุรกิจ | มีพื้นที่งาน (stage 15) และข้อมูลยืนยันแล้ว ไม่เปลี่ยนหลังยืนยัน · ลูกค้าเดิมไม่มีพื้นที่งาน = ลูกค้าตรวจเอง |
| สิทธิ์ | ลูกค้าอนุมัติเอง หรือลูกค้าเปิดอนุญาตให้เราเผยแพร่ (`publish_allowed`) · ทีมเผยแพร่แทนลูกค้าเดิมไม่ได้ |
| schema ตรงกับข้อความ | คำถามใน FAQPage ต้องมีในเนื้อหา · ชื่อ Organization/LocalBusiness ตรงกับแบรนด์ · JSON อ่านได้ |
| ไม่ซ้ำ | ชื่อไม่ซ้ำกับชิ้นที่เผยแพร่แล้ว · เนื้อหาซ้ำไม่ถึง 80% |
| ลิงก์ | ไม่มี `javascript:` / localhost / example.com / TODO / ลิงก์ไม่มีโปรโตคอล |
| ความเกี่ยวข้อง | มีชื่อและเนื้อหาพอ |
| ขอบเขต | มีพื้นที่งาน = มีงานเนื้อหาในแผนที่อนุมัติ |
| สิทธิ์เข้าถึง | ยังตรวจผ่านอยู่ |
| ความสามารถปลายทาง | ปลายทางทำการนั้นได้จริง (ตารางด้านล่าง) |

| ปลายทาง | สร้าง | แก้ | ถอน | คืนเวอร์ชันเดิม |
|---|---|---|---|---|
| WordPress / ตัวเชื่อม | ✓ | ✓ | ✓ | ✓ |
| หน้า hosted | ✓ | ✓ | ✓ | ✗ |
| หน้าเดิมที่ทีมเว็บลูกค้าดูแล | ✗ | ✗ | ✗ | ✗ |

ปลายทางทำไม่ได้ → สถานะ `limited` และสร้างงานให้ทีมเว็บลูกค้าในพื้นที่งาน ระบบไม่อ้างว่าเผยแพร่แล้ว

## 2. สถานะและการอนุมัติ

`draft → reviewed → approved → dispatching → published` · `failed` · `uncertain` · `limited` · `rolled_back`

- **การอนุมัติ**
    - ผูกกับ hash ของเนื้อหา ปลายทาง และ id คำขอ (`jobs.grant`/`consume`) ใช้ได้ครั้งเดียว อายุ 72 ชั่วโมง
    - ระบบตรวจประตูซ้ำตอนอนุมัติ
- **เนื้อหาเปลี่ยนหลังอนุมัติ** → ไม่ส่ง ยกเลิกการอนุมัติ และกลับเป็นร่าง เวอร์ชันใหม่ต้องสร้างคำขอใหม่
- **สิทธิ์ถูกถอนหรือปลายทางเปลี่ยนก่อนส่ง** → `failed` และไม่ส่ง
- **"เผยแพร่แล้ว"** ต้องให้ปลายทางยืนยัน (ตรวจลิงก์ได้ 200 ตอบ True ได้ 404/410 ตอบ False)
    - ส่งแล้วแต่ยืนยันไม่ได้ หรือหมดเวลา → `uncertain`
- **ห้ามส่งซ้ำมั่ว**
    - คำขอที่ส่งไปแล้ว กดส่งอีกไม่ได้
    - กดเผยแพร่ซ้ำด้วยเวอร์ชันเดิม จะได้คำขอเดิม (คีย์กันซ้ำ)
    - ใช้ "ตรวจปลายทาง" (`reconcile`) หาด้วย id/ลิงก์เดิม ถ้าหาไม่เจอให้คงสถานะ uncertain ไม่เดา
- **คืนเวอร์ชัน**
    - กระทบเฉพาะชิ้นนั้น
    - มีเวอร์ชันก่อนหน้า → ส่งเวอร์ชันที่เผยแพร่ครั้งก่อนกลับไป
    - ไม่มีเวอร์ชันก่อนหน้า → ถอนการเผยแพร่
    - ปลายทางทำไม่ได้ → บันทึกข้อจำกัด โดยยังนับว่าเผยแพร่เวอร์ชันนี้อยู่
- **เมื่อเปิด flag**
    - ไม่มี auto-publish
    - "ซ่อม AEO ทั้งหมด" ไม่เผยแพร่ซ้ำเอง
    - ปุ่ม "เผยแพร่ (public)" ของลูกค้าเดินตามประตูนี้ ส่วนการส่งเป็นร่างเข้า WordPress ยังเหมือนเดิม

## 3. ผลรายเดือน (`retention.review`)

รายงานแยก 4 หมวด:
1. งานที่ส่งมอบ
2. เว็บ/การค้นหา
3. AI ที่สังเกตได้
4. ผลทางธุรกิจ (ไม่รู้ = บอกว่าไม่รู้)

- AI เทียบได้เฉพาะชุดคำถามและเครื่องมือเดียวกัน (`qset` เก็บตอนวัดผลตั้งต้น) ชุดต่างกันจะขึ้นว่า "เทียบกับค่าตั้งต้นไม่ได้"
- บอกเรื่องระยะหน่วงเสมอ และไม่อ้างว่างานไหนทำให้ตัวเลขขยับ
- "ข้อมูลยังไม่พอสรุปในเดือนนี้" เป็นผลรายเดือนที่ถูกต้อง

## 4. ดูแลลูกค้าตามขั้น

สำหรับลูกค้าที่มีพื้นที่งาน:
- ติดขั้น (รอข้อมูล / รอสิทธิ์ / ติดปัญหา) เกิน 3 วัน → บันทึกและเตือนทีมภายใน ครั้งเดียวต่อขั้น โดยไม่ใช้อีเมลเตือนติดตั้งตามวันแบบเดิม
- รายงานรายเดือนส่งเมื่อมีผลวัดตั้งต้นแล้วเท่านั้น ถ้ายังไม่มีจะบันทึกว่ารอ

## 5. ขยายบัญชี (`retention.fit_reason`)

- ใช้เยอะอย่างเดียวไม่พอ ต้องติดตั้งแล้วและเผยแพร่แล้วอย่างน้อย 3 ชิ้น
- ถ้ามีพื้นที่งาน ต้องส่งมอบได้อยู่ ถ้ายังรอข้อมูล ติดปัญหา หรือยกเลิก = ไม่เสนอ ระหว่างกำลังทำขอบเขตเดิม เสนอได้แค่รายปี
- ลูกค้าที่ขอไม่รับการติดต่อ = ไม่เสนอ
- เหตุผลที่เหมาะต่อท้ายในข้อเสนอให้คนตรวจ และทุกข้อเสนอยังต้องรอเจ้าของอนุมัติเหมือนเดิม
- รายปี / ซื้อเพิ่ม / ขออนุญาตทำเคส แยกกัน ระบบไม่ตัดเงิน ไม่อัปเกรด และไม่เผยแพร่เคสเอง

## ยังไม่ครอบคลุม

- ระบบยังหาคำขอที่ไม่แน่ใจผลบน WordPress ด้วยคีย์กันซ้ำไม่ได้ (`find` ยังเป็น None) ต้องอาศัย id/ลิงก์ที่ปลายทางตอบกลับมา
- ยังไม่มีช่องให้ลูกค้ากรอกผลทางธุรกิจ
- ยังไม่ได้ทดสอบกับ WordPress จริง ยังไม่ได้ทดสอบ Postgres และหน้าใหม่ยังเป็นภาษาไทยอย่างเดียว
